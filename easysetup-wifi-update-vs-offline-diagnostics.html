WIFI_UPDATE 与 OFFLINE_DIAGNOSTICS
联系、区别，以及各自到底做了什么

两个宏在 Kconfig 里紧挨着，在状态机里被同一个 A || B 条件捆在一起， 但一个走 MQTT、一个走 BLE；一个要 capability、一个不要。 这篇把 8 处引用点全部摊开，顺带揪出一个名字骗人的运行时字段。

代码总量 8 处宏引用 · 6 处赋值点 关联页面 offline-diagnostics-deep-dive.html 验证工程 apps/esp32/light_example

结论先行

它们是同一个开关的两种用途：
「配网完成后 BLE 别关」这件事，开了谁都能成立。
  • 共同点只有一个，但很硬：4 处 #if defined(A) || defined(B) 把二者绑在同一组条件编译上。 开任意一个，设备配完网后 BLE 就常驻广播。这解释了"配网完成后手机还能搜到设备"。
  • 区别在"BLE 留下来之后干什么"： WIFI_UPDATE 让手机改设备的 WiFi（复用配网命令 + MQTT 上报结果）； OFFLINE_DIAGNOSTICS 让手机问设备哪里坏了（新增专用命令，纯 BLE）。
  • 依赖完全不同：WIFI_UPDATE 要 Device Profile 里声明 wifiInformation capability； OFFLINE_DIAGNOSTICS 零 capability 依赖。
  • 一个被名字骗了的字段：ctx->wifi_update_enabled 跟 WIFI_UPDATE 宏没有关系， 它是"这台设备已经完成过配网注册"的 owned 标志，冷启动从 NV 读出来就置 true。 而它恰恰是离线诊断的前置条件。

01共同点：同一组开关

Kconfig 里两段紧挨着，结构一模一样（iot-core/src/Kconfig:37-49）： 

config STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE
    bool "Enable wifi update functionality"
    default n
    depends on STDK_IOT_CORE_EASYSETUP_BLE           // 第 37-42 行
    help
       If this option is enabled, The device enable wifi update functionality.

config STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS
    bool "Enable offline diagnostics functionality"
    default n
    depends on STDK_IOT_CORE_EASYSETUP_BLE           // 第 44-49 行
    help
       If this option is enabled, the device enable offline diagnostics functionality.

两个都 default n，两个都硬依赖 BLE。没有 BLE，谁都开不起来。

注意 depends on 的含义

depends on STDK_IOT_CORE_EASYSETUP_BLE 是编译期依赖，不是运行时。 ESP32 上 CONFIG_STDK_IOT_CORE_EASYSETUP_BLE=y 是默认开的，所以这条平时不会卡住你。 但如果哪天你为了省 flash 关了 BLE，这两个选项会一起从 menuconfig 里消失 —— 不是 bug，是 Kconfig 的规矩。

1.1 四处 OR 条件：真正的绑定

全工程搜 CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS， 在 src/ 下只有 5 处，其中 4 处都是跟 WIFI_UPDATE 做 OR。

位置形式作用
iot_main.c:337 A \|\| B PROV_ENTER → CLOUD_DISCONNECTED 时调 iot_ble_ctrl_request()，让 BLE 继续跑
iot_main.c:384 A \|\| B PROV_SLEEP → CLOUD_DISCONNECTED 时同上
iot_main.c:418 A \|\| B PROV_CONFIRM → CLOUD_DISCONNECTED 时调 iot_easysetup_start_ble_advertisement() 重新起广播
iot_easysetup_ble.c:182 !(A \|\| B) BLE 断开回调里：两个都没开才 _send_ble_deinit_request() 关 BLE
iot_easysetup_d2d_ble.c:2222 仅 B 离线诊断两个 handler 的实现体（唯一非 OR 的一处）

第 4 处代码长得是反的，值得单独看一眼：

/* iot_easysetup_ble.c:182，BLE 断开回调里 */
#if !(defined(CONFIG_STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE) || \
      defined(CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS))
    // If there is no other ble service required except onboarding,
    // cleanup after onboarding complete.
    if (context->wifi_update_enabled) {
        _send_ble_deinit_request();      // 关掉 BLE 广播
    }
#endif

读法：只有当 WiFi Update 和离线诊断都没有开启时，配网完成后才主动关 BLE。 开了任意一个，这段代码根本不参与编译，BLE 就一直保持着。

这解释了你的实测现象

你之前观察到「light_example 配完网后手机还能搜到设备」，以为哪里没清理干净。 实际上是因为 sdkconfig.esp32s3:1466 里 CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS=y —— 这行让上面那个 #if 整段失效，BLE 从此常驻。设计如此。

02区别总表

WIFI_UPDATE

CONFIG_STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE
  • 场景：换路由器、改密码，不想删设备重配
  • 方向：双向（云端下发 → BLE 推凭据 → MQTT 报结果）
  • 通道：BLE（收） + MQTT（报）
  • 要 capability：要 wifiInformation
  • 要 otm_confirmed：不要
  • 离线可用：不可（云端下发前提）
  • 新增命令：无，复用配网的 Cmd 6
  • 你的工程：not set

OFFLINE_DIAGNOSTICS

CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS
  • 场景：设备显示离线，让用户当场查原因
  • 方向：单向（手机问 → 设备答）
  • 通道：纯 BLE，完全不碰 MQTT
  • 要 capability：不要，零依赖
  • 要 otm_confirmed：要（先走完 Cmd 1~4）
  • 离线可用：可，这就是它的主场
  • 新增命令：Cmd 11 connectionInfo / Cmd 12 recovery
  • 你的工程：=y
维度WIFI_UPDATEOFFLINE_DIAGNOSTICS
宏出现总次数8 处（含 stdkconfig.cmake:27）6 处（含 stdkconfig.cmake:28、3 处测试）
src/ 下独有引用3 处：iot_api.c:2069、iot_main.c:586、iot_internal.h:5110 处 —— 除了 4 处 OR，只剩实现体那一个 #if
改状态机吗改：影响 Cmd 6 走 CLOUD_DISCONNECTED 还是 PROV_DONE不改：只挂两个新命令
改 OTM 列表吗改：已配网时只给 Hashed SN不改（但受这个改动间接影响，见第 5 节）
吃 rate limit 吗吃：iot_update_wifi_info 会检查 ctx->rate_limit不吃：BLE 通道，与 MQTT 配额无关
省电影响两者相同：都让 BLE 常驻广播，都会增加待机功耗。要低功耗得自己控制广播间隔或关掉

03WIFI_UPDATE 的五处作用

这个宏不只"开个功能"，它实际改写了五段逻辑。

3.1 放开 BLE 常驻

就是第 1.1 节那四处 OR 条件，不再重复。

3.2 连云成功后主动上报 WiFi 信息

触发点在 iot_main.c:585-592，状态机切到 IOT_STATE_CLOUD_CONNECTED 时：

case IOT_STATE_CLOUD_CONNECTED:
#if defined(CONFIG_STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE)
    iot_update_wifi_info(ctx);              // ← 每次连云成功都发一次
#endif
    iot_cap_call_init_cb(ctx->cap_handle_list);   // 然后才初始化 capability
    ctx->status_cb(ST_DEVICE_STATUS_CLOUD_CONNECTED, ctx->status_usr_data);
    break;

注意顺序：先发 WiFi 信息，再初始化 capability。因为 wifiInformation 不是普通 capability， 它是直接拼 MQTT 事件发出去的（iot_api.c:2175 的 iot_update_wifi_info()）。

这条事件里装三个属性：

属性数据来源备注
ssid ctx->prov_data.wifi.ssid NV 里存的，不是实时查询。所以如果设备实际连的 AP 和 NV 里记录的不一致（比如手动改过），这里会报旧值
supportedWiFiFrequencies iot_bsp_wifi_get_freq() 返回枚举 IOT_WIFI_FREQ_2_4G_ONLY，映射成 ["2.4G"]
supportedWiFiAuthTypes iot_bsp_wifi_get_auth_mode() 位掩码，逐位翻成 OPEN/WEP/WPA-PSK/… 字符串数组

每个事件都带一份 providerData（iot_api.c:2079）：

{
  "sequenceNumber": 3,
  "timestamp": "1762741800000",     // 毫秒时间戳
  "stateChange": "Y"                 // 强制标记为状态变更，绕过 ATTR_CACHE 去重
}
它会吃掉你的发布配额

iot_api.c:2187 有一道检查： 

if (ctx->rate_limit) {
    IOT_WARN("Exceed rate limit. Can't send attributes for a while");
    return IOT_ERROR_BAD_REQ;      // 直接放弃，不重试
}

也就是说 每次重连都会发 3 条 deviceEvents（其实是 1 个 publish 带 3 个 item，算 1 条）。 如果你在做限流测试、设备反复重连，这些上报会占用 50 条/分钟的配额，而且被限流时是静默丢弃， 只在串口打一行 WARN。这跟你之前调 rate limit 时看到的计数偏差可能有关。

3.3 改变 Cmd 6 的落点：只重连，不重注册

这是 WiFi Update 存在的根本理由，在 iot_easysetup_d2d_ble.c:2081-2109：

ctx->d2d_event_request = true;
ctx->need_wifi_reset = true;
ctx->connection_retry_count = 0;

if (ctx->wifi_update_enabled) {
    // 已配过网 → 只断开云端重连，deviceId / 用户设置全部保留
    if (ctx->next_connection_retry_timer) {
        iot_os_timer_delete(ctx->next_connection_retry_timer);
        ctx->next_connection_retry_timer = iot_os_timer_create(_next_connection_retry_timeout, 2000, ctx);
        iot_os_timer_start(ctx->next_connection_retry_timer);
    } else {
        IOT_INFO("send  DISCONNECTED");
        iot_state_update(ctx, IOT_STATE_CLOUD_DISCONNECTED, 0);   // ← 关键分支
    }
} else {
    // 首次配网 → 走完整注册流程
    IOT_INFO("send  PROV_DONE");
    iot_state_update(ctx, IOT_STATE_PROV_DONE, 0);            // ← 会去云端注册
}
这一行分支就是整个功能的价值

走 PROV_DONE = 重新注册，云端会当成一台新设备，用户的房间分配、自动化场景、设备名全丢。
走 CLOUD_DISCONNECTED = 只是换个 AP 重连，deviceId 不变，云端眼里还是同一台设备。
WiFi Update 的全部意义就是让第二次走下面那条路。

3.4 跳过 cloud_prov 解析

iot_easysetup_d2d_ble.c:1992-1999：

if (!ctx->wifi_update_enabled) {
    iot_api_prov_data_mem_free(&ctx->prov_data);
    err = _es_cloud_prov_parse(ctx, (char *)in_payload);   // 解析 mnid/setupid/注册信息
}

已配网设备不需要重新提交 mnid / setupId 这些云端注册信息 —— NV 里都有。 少解析一段 JSON，也少了内存分配（iot_api_prov_data_mem_free 那一行在已配网时也被跳过）。

3.5 把 OTM 列表压成只剩 Hashed SN

iot_easysetup_d2d_ble.c:706-716，处理 Cmd 3（ConfirmInfo）时：

if (ctx->wifi_update_enabled) {
    // 已配网 → 只提供一种 OTM
    JSON_ADD_ITEM_TO_ARRAY(array, JSON_CREATE_NUMBER(OVF_BIT_HASHED_SERIAL_NUMBER));
} else {
    // 首次配网 → 遍历 devconf 里配置的所有 OTM 方式
    for (i = OVF_BIT_JUSTWORKS; i <= OVF_BIT_MAX_FEATURE; i++) {
        if ((i == OVF_BIT_JUSTWORKS) && ctx->add_justworks) {
            JSON_ADD_ITEM_TO_ARRAY(array, JSON_CREATE_NUMBER(i));
        } else if (ctx->devconf.ownership_validation_type & (unsigned)(1 << i)) {
            JSON_ADD_ITEM_TO_ARRAY(array, JSON_CREATE_NUMBER(i));
        }
    }
}

_es_is_otm_feature_supported()（同文件 1087 行）也做了同样的收窄： 

if (ctx->wifi_update_enabled) {
    confirm_support = ((1u << confirm_feature) & (1u << OVF_BIT_HASHED_SERIAL_NUMBER));
} else {
    confirm_support = ((1u << confirm_feature) & ownership_validation_type);
}
为什么这么做：重连时不用再按按钮

首次配网时，用户可能要按设备上的按钮、输入 PIN、扫二维码来证明"我是主人"。 但设备已经配过网了 —— 云端有它的序列号记录，App 也知道。 这时候用 Hashed Serial Number 直接验，用户什么都不用做，连上就自动确认。
这就是 WiFi Update 和离线诊断能"静默"工作的前提。

04OFFLINE_DIAGNOSTICS 的两处作用

这个宏比上面那个简单得多，只做两件事。

4.1 放开 BLE 常驻

同一组四处 OR 条件。

4.2 挂上两个新命令的 handler

iot_easysetup_d2d_ble.c:2222 是整个 src/ 下唯一一处独立引用：

#if defined(CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS)
STATIC_FUNCTION iot_error_t _es_offline_diagnostics_connection_info_handler(...)  { /* 2223 */ }
void offline_diagnostics_wifi_update_command_handler(...)                        { /* 2295 */ }
STATIC_FUNCTION iot_error_t _es_offline_diagnostics_recovery_handler(...)        { /* 2382 */ }
#else
// 三个桩函数，全部 return IOT_ERROR_EASYSETUP_NOT_SUPPORTED
#endif

不开启时，iot_easysetup_get_response() 里那两个 case 依然存在、依然会被命中， 只是调到的函数立刻返回 NOT_SUPPORTED。所以 App 会收到一个明确的"不支持"， 而不是"命令号非法"。

它在 MQTT 侧和 capability 侧的动作：零

全工程搜 OFFLINE_DIAGNOSTICS 的 6 处引用，没有一处涉及 st_cap_*、iot_mqtt_publish、wifiInformation。 这个宏纯粹是"给 BLE 加两个命令 + 别关 BLE"。

05隐藏主角：wifi_update_enabled

这个名字是骗人的

ctx->wifi_update_enabled 跟 CONFIG_STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE 宏 没有任何关系。不开那个宏，这个字段照样存在、照样被赋值、照样影响行为。

它的真实语义是：这台设备是否已经完成过一次配网注册（owned）。

它在 iot_main.h:427 定义，注释也印证了这一点：

bool wifi_update_enabled;      /**< @brief to check onboarding completion status*/

注释写的是 "onboarding completion status"，不是 "wifi update feature enabled"。

5.1 六个赋值点

值位置触发条件
falseiot_main.c:98启动时 NV 里没有 prov_data → 当成新设备，进配网
falseiot_main.c:109prov_data 校验失败（SSID 空、格式坏）→ 清 NV 重配
falseiot_main.c:115有 prov_data 但没有 deviceId → 注册没完成，重来

falseiot_main.c:1702start_from_onboarding = true（用户主动要重新配网）→ 故意降级成新设备

另外还有两个内部维护点（iot_easysetup_ble.c:641 / 645），在 BLE deinit 路径里根据 es_network_status 再校正一次。

5.2 OTM 自动确认链：把三者串起来

这是把 wifi_update_enabled、otm_confirmed、离线诊断三者串成一条线的关键， 也是上一份页面里没讲透的部分。

设备已配网，wifi_update_enabled = true
iot_main.c:133 / 914
上电从 NV 读到 prov_data + deviceId，或首次注册刚完成。
App 连上 BLE，发 Cmd 3（ConfirmInfo）
iot_easysetup_d2d_ble.c:706
设备只返回一个 OTM：OVF_BIT_HASHED_SERIAL_NUMBER（值 6）。 不再给 QR / 按钮 / PIN 这些需要用户动手的方式。
App 用 hashed serial number 自动发 Cmd 4（Confirm）
iot_easysetup_d2d_ble.c:1187-1226
设备算 SHA512(serialNumber)，跟 App 传来的比对。一致就通过 —— 用户全程无感。
otm_confirmed = true
iot_easysetup_d2d_ble.c:1226 / 1348

这条链断了会怎样

如果设备的 serialNumber 没在 Developer Workspace 正确登记， App 的 hashed SN 对不上 → Cmd 4 返回 IOT_ERROR_EASYSETUP_INVALID_HASHED_SERIAL_NUMBER （iot_easysetup_d2d_ble.c:1221）→ otm_confirmed 永远是 false → 离线诊断和 WiFi Update 双双不可用，而且串口只会打一行 "OVF_BIT_HASHED_SERIAL_NUMBER confirm fail"，从 App 侧看就是"诊断功能没反应"。

你之前遇到过的 81-001（No device data in server）就是这条链的前置问题。

06四种组合矩阵

WIFI_UPDATEOFFLINE_DIAG实际行为适用场景
nn 配网完成 → BLE 立即 deinit，不再广播。设备最省电，但出问题只能删除设备重配。 电池供电、对功耗极度敏感的量产设备
yn BLE 常驻。云端可下发新 WiFi 凭据，设备走 CLOUD_DISCONNECTED 重连不重注册。连云时上报 wifiInformation。手机无法主动查故障。 固定供电、路由器经常换的家庭设备
ny BLE 常驻。手机可以查故障、可以推新 WiFi、可以重启设备，但云端不知道设备连的哪个 AP，也不能远程发起换 WiFi。← 你的当前配置 调试阶段、需要现场排障的设备
yy 全功能：云端有 WiFi 视图 + 可远程换 WiFi + 手机可现场诊断。 量产设备的标准配置
别被第三行误导

n / y 配置下，Cmd 12 的 updateWifi 命令照样能换 WiFi （iot_easysetup_d2d_ble.c:2420-2465），它复用 _es_wifi_prov_parse() 和 d2d_event_request / need_wifi_reset 那一整套逻辑。

区别只在谁发起：
· WIFI_UPDATE → 云端下发命令，App 被动执行，设备在线时随时可做
· OFFLINE_DIAG → 手机在 BLE 连接上现场推，只在设备离线时的诊断流程里出现

所以缺的不是"换 WiFi 能力"，而是远程换的能力 + 云端那份 WiFi 视图。

07与 wifiInformation capability 的三方关系

这三个东西名字都带 WiFi，边界必须画清楚。

问题答案
不开 WIFI_UPDATE，wifiInformation capability 能单独用吗？能。它就是个普通 capability，你自己 caps_wifiInformation_initialize() 注册即可。但 STDK 自带的自动上报逻辑（iot_update_wifi_info）不会编进去，得自己发。
开了 WIFI_UPDATE，Device Profile 忘了声明会怎样？MQTT publish 的 payload 里 capability 名是 "wifiInformation"，云端找不到对应定义会丢弃或报错。设备侧不一定有日志，表现为"云端看不到 SSID"。
OFFLINE_DIAG 需要它吗？完全不需要。两者在代码层面零交叉。

08两个真实缺陷

8.1 ap_freq 在 ESP32 上恒为 0

离线诊断的 Cmd 11 会回一个 ap_freq 字段，代码这么写的（iot_easysetup_d2d_ble.c:2271）：

JSON_ADD_NUMBER_TO_OBJECT(con_info, "ap_freq", (double)iot_bsp_wifi_get_freq());

看着像"AP 频率（MHz）"。但 iot_bsp_wifi_get_freq() 返回的是枚举，不是频率：

/* src/include/bsp/iot_bsp_wifi.h:48-52 */
typedef enum {
    IOT_WIFI_FREQ_2_4G_ONLY = 0,
    IOT_WIFI_FREQ_5G_ONLY,
    IOT_WIFI_FREQ_2_4G_5G_BOTH,
} iot_wifi_freq_t;

/* src/port/bsp/esp32/iot_bsp_wifi_esp32.c:578-581 */
iot_wifi_freq_t iot_bsp_wifi_get_freq(void)
{
    return IOT_WIFI_FREQ_2_4G_ONLY;      // 写死，恒等于 0
}

所以 ap_freq 在 ESP32 上永远是 0，不是 2437，也不是 2412。

使用方期望语义实际拿到
WIFI_UPDATE 的 supportedWiFiFrequencies设备支持的频段枚举["2.4G"] —— 正确
OFFLINE_DIAG 的 ap_freqAP 信道频率 MHz0 —— 错误

同一个函数被两种语义复用。要拿真实频率得自己调 esp_wifi_sta_get_ap_info() 的 primary 信道换算（2412 + (ch-1)*5，信道 14 特殊）。

8.2 已配网时 OTM 只剩 Hashed SN 的副作用

第 3.5 节说过：wifi_update_enabled = true 时，Cmd 3 只返回 OVF_BIT_HASHED_SERIAL_NUMBER。这带来两个连锁问题：

serialNumber 未登记
hashed SN 校验失败 → IOT_ERROR_EASYSETUP_INVALID_HASHED_SERIAL_NUMBER → otm_confirmed 永远 false → 诊断和换 WiFi 全废
设备被删除过但 NV 没清干净
本地还以为自己 owned，只给 hashed SN；云端已经不认这台设备了。表现为"连得上 BLE，但什么都做不了"。解法：按钮长按 / cleanup 命令清 NV
开发者想手动测 QR / 按钮方式
已配网设备上没有这些选项了。_es_is_otm_feature_supported() 会直接判不支持。要测只能先清掉配网数据

9.3 验证 wifi_update_enabled 跟宏无关

当前配置里 WIFI_UPDATE 是 not set，但下面这些行为照样发生 —— 只要在串口里搜关键字就能看到：

串口日志说明

publish event, topic : .../events, payload :

9.4 抓一次 wifiInformation 上报（要临时开宏）

  1. idf.py menuconfig → STDK IoT Core → Easysetup → 勾上 WIFI Update
  2. 重编烧录，让设备连上云
  3. 串口会打出一段 deviceEvents，结构如下：

      "attribute":"ssid", "value":"MyAP",

10决策树：我该开哪个

只要调试方便
开 OFFLINE_DIAGNOSTICS。零 Profile 改动、零 capability、能查错误码能远程重启能换 WiFi，成本最低。你现在的选择是对的。
量产设备，用户会换路由器
两个都开。云端需要 wifiInformation 那份视图来判断"该不该建议用户换 WiFi"，也需要远程下发凭据的能力。
电池供电，功耗敏感
两个都关。代价是设备一旦配网出问题只能删除重配。折中方案：保持关闭，但保留长按按钮触发 st_conn_cleanup 的入口。
只想让云端知道设备连的哪个 AP
开 WIFI_UPDATE 即可，不用开诊断。但注意它会改变 Cmd 6 的落点和 OTM 列表，等于顺带把重连流程也改了。
已经开了诊断，还想加云端视图
再把 WIFI_UPDATE 打开，然后去 Profile 加 capability。注意两处都会让 BLE 常驻，叠加不会额外增加广播开销（本来就常驻）。
