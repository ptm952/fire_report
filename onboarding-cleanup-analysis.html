STDK 配网清理行为变更分析

从 v2.3.2 到 v2.4.2，官方 CHANGELOG 只用一行描述了这次变更： Remove device cleanup during Onboarding process。 本文把它背后的完整代码路径、真实风险、以及三方升级需要注意的点全部拆开。

0 · 结论速览

BUG 本质
用易变的 RAM 标志
决定擦不擦持久数据
wifi_update_enabled 是内存 bool，被多条路径刷成 false；而它决定的是 NV 里 device ID 的生死。
修复思路
拆成两件事：
重置网络 ≠ 重置身份
断线只置 need_wifi_reset 让 WiFi 重连；销毁身份必须显式调 st_conn_cleanup()。
影响面
两处 device 擦除路径
被同时移除
① BLE 断线回调 ② st_conn_start_ex 重复调用。后者对三方更危险，文档完全没提。

后果的严重性：iot_device_cleanup() 会执行 iot_nv_erase(IOT_NVD_DEVICE_ID)。device ID 一旦被擦，设备下次连云端会重新注册成一台全新设备，拿到新的 deviceId。用户在 SmartThings App 里的房间归属、自动化、场景引用全部失效。

1.2 iot_device_cleanup() 到底清了什么

两版实现一致（v2.3.2 iot_api.c:1029 / v2.4.2 iot_api.c:1316）：

iot_error_t iot_device_cleanup(struct iot_context *ctx)
{
    IOT_INFO("start to erase device information");
    //            ↑ 这是日志里唯一的线索

    /* (a) 清内存 */
    iot_api_prov_data_mem_free(&(ctx->prov_data));
    memset(&(ctx->prov_data), 0x0, sizeof(ctx->prov_data));

    if (ctx->iot_reg_data.dip)        { iot_os_free(...); ... }
    if (ctx->iot_reg_data.locationId) { iot_os_free(...); ... }
    memset(&ctx->iot_reg_data, 0x0, sizeof(ctx->iot_reg_data));

    /* (b) 擦 NV —— 不可逆 */
    iot_err = iot_nv_erase_prov_data();      // WiFi SSID/密码/BSSID/加密方式 + DIP
    iot_err = iot_nv_erase(IOT_NVD_DEVICE_ID); // device ID ← 设备身份

    /* (c) 断链 */
    if (ctx->evt_mqttcli != NULL) iot_es_disconnect(ctx, IOT_CONNECT_TYPE_COMMUNICATION);
    if (ctx->reg_mqttcli != NULL) iot_es_disconnect(ctx, IOT_CONNECT_TYPE_REGISTRATION);

    /* (d) 释放 lookup_id */
    if (ctx->lookup_id) { iot_os_free(ctx->lookup_id); ctx->lookup_id = NULL; }
}

不是清 WiFi，是连设备身份一起清。很多人以为这只是"忘记 WiFi 密码"，实际上 IOT_NVD_DEVICE_ID 一起被擦。重新配网时设备拿空身份去注册，云端分配全新 deviceId。

2 · 2.3.2 的问题究竟是什么

问题 22.3.2 问题在哪？为什么这算 bug？

2.1 判断依据太弱，被破坏的东西太重

断线回调里的判断条件只有一个 bool：

if (context->wifi_update_enabled == false) {
    iot_device_cleanup(context);   // 擦 NV：凭据 + device ID
}
维度判断依据被破坏的对象
存在位置RAM（bool 字段）NV flash（持久化）
生命周期本次运行，重启即重置永久，断电不可恢复
可靠性被 5+ 条路径改写一擦就没了
语义"本次配网是否成功过""设备在这个账号里的身份"

两者严重程度完全不对等。一个随时可能被改写的运行时标志，决定了永久数据的生死。

2.2 这个标志会被哪些路径刷成 false

wifi_update_enabled 在 v2.3.2 里共有 6 处赋值：

位置赋值触发场景
iot_main.c:132falseNV 里没有 prov data
iot_main.c:144falseprov data 校验失败（_check_prov_data_validation）
iot_main.c:151falseNV 里没有 device ID
iot_main.c:171true读到有效 device ID（正常启动）
iot_main.c:683true注册成功（IOT_COMMAND_CLOUD_REGISTERED）
iot_easysetup_ble.c:633falseiot_easysetup_deinit() 在 !es_ble_ready 时无条件置 false

最后一条是杀手。而它前面还套了一层：

// iot_api.c:1674-1679  iot_cleanup()
if (ctx->es_ble_ready) {
    ctx->es_ble_ready = false;        // ← 先置 false
    iot_easysetup_deinit(ctx);        // ← 再调 deinit → 必然走 !es_ble_ready 分支
}
iot_device_cleanup(ctx);            // ← 无条件擦

也就是说：任何一次 iot_cleanup()、任何一次"非 BLE-ready 状态的 deinit"，都会把 wifi_update_enabled 刷成 false，而 NV 里的 device ID 还好端端躺着。

之后只要 BLE 再断一次 → 命中 cleanup 分支 → 真数据被当成垃圾擦掉。

4 · st_conn_start_ex() 的陷阱

问题 4先调 st_conn_start()，后来又因为重连或 UI 触发调了一次 st_conn_start_ex()，为什么会清空设备信息？

4.1 三个 API 的行为对比

函数版本curr_state != INITIALIZED 时擦 NV？
st_conn_start()2.3.2报 IOT_ERROR_BAD_REQ 直接返回否
st_conn_start()2.4.2同上（代码逐字相同）否
st_conn_start_ex()2.3.2iot_cleanup(ctx, false)是
st_conn_start_ex()2.4.2无此分支，按状态分派否

同一个"状态不是 INITIALIZED"的情况，两个 API 给出完全相反的处理：

// st_conn_start() —— 保守
IOT_WARN("Can't start it, iot_main_task is already working(%d)", ctx->curr_state);
iot_err = IOT_ERROR_BAD_REQ;
goto end_st_conn_start;            // 拒绝，什么都不改

// st_conn_start_ex() —— 激进
IOT_WARN("iot-core is already working(%d), stop & remove all cmd first", ctx->curr_state);
iot_cleanup(ctx, false);           // 全擦了重新来

4.2 为什么条件必然成立

ctx->curr_state 在整个 v2.3.2 里只有 3 个写入点：

位置写入值说明
iot_main.c:499new_state状态机推进（→ 5 / 6 / 3 …）
iot_main.c:1509INITIALIZEDst_conn_start_ex 自己强制写
iot_api.c iot_cleanup() 末尾INITIALIZED清理时写

没有第四条路径会把它写回 INITIALIZED。而 st_conn_start() 一启动，状态机就开始爬：

st_conn_start()
  → _check_prov_status()
      → iot_state_update(CLOUD_DISCONNECTED)   // 只是入队，异步
          → work queue 线程 → _do_state_updating()
              → ctx->curr_state = 5           // iot_main.c:499
  → 连上云端 → ctx->curr_state = 6

所以第一次 st_conn_start() 之后，curr_state 永久停在 5 或 6。任何时刻再调 st_conn_start_ex()，判断都是 100% 成立。

两个命名陷阱

陷阱一：false 不是"软清理"

iot_cleanup(ctx, false);
//                 ↑ 这是 reboot 参数

// 函数体里：
iot_device_cleanup(ctx);   // ← 无条件擦
if (reboot) { IOT_REBOOT(); } // ← false 只控制"擦完别重启"

陷阱二：cleanup 这个名字有歧义

在多数代码库里 cleanup 指"释放资源、停止服务"。但 STDK 这个 iot_cleanup 的实际语义是：把 SDK 恢复到刚 st_conn_init() 完成、还没做过任何配网的状态。"刚 init 完"意味着内存和 NV 都干干净净——所以它必须擦 NV。

v2.3.2 里不存在"只停服务、不动数据"的中间档操作。要么什么都不做，要么全擦。

4.3 竞态窗口：为什么有人测不出来

iot_state_update() 只做入队，不同步更新 curr_state（iot_api.c:240-258）：

iot_error_t iot_state_update(struct iot_context *ctx, iot_state_t new_state, int opt)
{
    struct iot_state_data state_data;
    state_data.iot_state = new_state;
    state_data.opt = opt;
    err = iot_command_send(ctx, IOT_COMMAND_STATE_UPDATE, &state_data, sizeof(...));
    return err;      // ← 立刻返回，curr_state 还没变
}
第二次调用的时机curr_state结果
第一次返回后、work queue 处理前（几毫秒窗口）INITIALIZED条件不成立 → 不清 → 侥幸没事
work queue 处理之后（绝大多数情况）5 / 6条件成立 → 清空

这解释了为什么会出现"本地测几十次都正常、上线后偶发设备变新设备"——取决于两次调用的时间间隔。

唯一存在的保护：只保护同线程

if (iot_os_thread_get_current_handle(&curr_thread) == IOT_OS_TRUE) {
    if (curr_thread == ctx->work_queue_thread) {
        IOT_WARN("Can't support it on same thread!!");
        return IOT_ERROR_BAD_REQ;      // ← 从 status_cb/noti_cb/cmd_cb 里调会被拒
    }
}

在回调里调是安全的（直接报错）。危险的是从其它线程调——UI 任务、按键任务、定时器任务。

为什么会写成这样

st_conn_start_ex() 是 v2.1 为 Ownership Transfer（OTM）引入的，带 start_from_onboarding / skip_usr_confirm 两个扩展参数。它的定位是"强制从头开始"——OTM 场景确实需要打断正在跑的会话。实现时把"强制停止"直接实现成了 iot_cleanup()，于是"停止"和"销毁"被绑在一起。

6 · 三方升级影响

问题 5这个机制和以往版本不一样，三方调用这个库的更新是不是得特意说明？

6.1 升级是安全的，不会破坏现有集成

这个改动只会减少清理，不会增加清理。第三方原有的 st_conn_cleanup() 调用完全不受影响，行为只会变得"更不容易丢数据"。不需要改任何调用代码。

6.2 但有一类集成必须提前告知

依赖旧行为当"隐式恢复出厂"的用法会失效。

有些集成把"BLE 配网中途断开"当作隐式重置手段——不清 NV 也能靠这个把设备打回未注册状态。v2.4.2 之后这条路走不通，必须显式调用：

st_conn_cleanup(iot_ctx, true);   // 现在这是唯一的清空方式

6.3 官方文档做得不够

位置是否说明
CHANGELOG 2.4.1只有一行 Remove device cleanup during Onboarding process，挂在 "Enhancements" 下
doc/APIs.mdst_conn_cleanup 文档两版完全一致，未提隐式调用点消失
doc/porting_guide.mdv2.4.2 只加了 6 行，与此无关
src/include/st_dev.h注释两版逐字相同

这是一个行为语义变更（隐式清理路径消失），却按普通 enhancement 处理。如果要写升级说明，建议这样措辞：

v2.4.1 起，BLE 配网流程中断开连接不再自动清除设备配网与注册数据。若需要恢复出厂（清除 device ID 与 WiFi 凭据），必须显式调用 st_conn_cleanup(iot_ctx, true)。

7 · 旧版本如何规避

问题 6以前版本三方使用，如果不想清理注册数据，是要把 cleanup 注释掉？

是的，只能改库代码，没有开关。

v2.3.2 里那行 iot_device_cleanup(context) 是无条件调用的，外面只包了 wifi_update_enabled == false 一个业务判断，没有 Kconfig、没有编译宏、没有运行时回调能拦。

方案代价
注释掉 iot_easysetup_ble.c:147要维护 fork 或 patch，每次同步上游都得重打
强制把 wifi_update_enabled 置 true影响状态机分支判定，副作用更大
不用 BLE EasySetup，自己实现配网太重，等于放弃 SDK 核心能力

方案一在有子模块的工程里更麻烦：bsp/esp32 指向 iot-core 子模块，注释完还要防止 git submodule update 覆盖回去，通常得改成自己的 fork URL 或加补丁脚本。

这大概正是官方愿意做这个改动的原因——让第三方不用再改库源码，把"清理"从隐式路径收拢到显式 API。从这个角度看，v2.4.2 对你现在的项目是净收益：之前那些"配网中途断开导致设备变新设备"的现象，在 v2.4.2 上不会再发生。
