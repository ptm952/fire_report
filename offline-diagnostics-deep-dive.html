离线诊断（Offline Diagnostics）依赖什么？
要不要 wifiInformation Capability？

从 BLE GATT 特征值写入，一路追到 JSON 响应回传，把这条链路上每一层的判定条件、编译开关、 运行时状态全部摊开。结论是：它完全绕开了 Capability 框架。

分析对象 iot-core/src/easysetup 参考文档 doc/Offline_Diagnostics.md · doc/BLE_Onboarding_ED25519.md 验证工程 apps/esp32/light_example

结论先行

离线诊断不依赖任何 Capability，也不需要 wifiInformation。
  • 它走的是 BLE 私有 GATT 通道（Service 0xFD1D / Char BE940F0E-AE2D-4F8E-A4C7-300280E60E09）， 报文是自定义二进制帧 + AES 加密 + JSON 负载，不经过 MQTT，也不经过 capability 层。
  • 它读的 WiFi 信息来自 BSP 层（iot_bsp_wifi_get_status()、iot_bsp_wifi_get_freq()）， 而不是 wifiInformation capability 的属性。
  • 它上报的错误码来自 STDK 内部的 ctx->last_st_ecode 状态字段，由 iot_set_st_ecode() 在网络/云连接各阶段写入，与设备 Profile 里声明了哪些 capability 无关。
  • 真正的前置条件只有四个：编译宏 CONFIG_STDK_IOT_CORE_EASYSETUP_BLE、 编译宏 CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS、 设备已配网（owned / wifi_update_enabled = true）、 以及一次完整的 BLE OTM 握手把 otm_confirmed 置 true。
  • wifiInformation 是 WiFi Update（换路由器不改配网） 功能的专属 capability， 两个功能经常被混为一谈，但代码路径、编译宏、依赖项全部独立。

01三条链路别混为一谈

STDK 里跟「WiFi 信息 / WiFi 出问题」沾边的机制有三套，名字很像、目的完全不同。 绝大多数「离线诊断要不要 wifiInformation」的困惑，都来自把这三者当成了一件事。

维度 离线诊断
Offline Diagnostics		 WiFi 更新
WiFi Update		 wifiInformation
Capability

看懂这张表就够了一半

你的 sdkconfig.esp32s3 第 1465~1466 行是这样的： 

# CONFIG_STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE is not set
CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS=y

离线诊断开着、WiFi 更新关着 —— 这个组合本身就证明了二者互不依赖： 如果离线诊断需要 wifiInformation，那它必然要依赖 WiFi Update 那条链路，而这里恰恰是关的。

1.1 wifiInformation capability 到底长什么样

它在 iot-core/src/include/caps/iot_caps_helper_wifiInformation.h 里定义，只有三个属性：

属性名类型 / 约束取值
ssidSTRING ATTR_SET_VALUE_REQUIRED设备当前连接的 SSID
supportedWiFiAuthTypesARRAYOPEN WEP WPA-PSK WPA2-PSK EAP SAE OWE FT-PSK
supportedWiFiFrequenciesARRAY2.4G 5G 6G

它的唯一使用点是 iot_api.c:2069 起的一段代码，整段被编译宏包着：

/* iot_api.c:2069 */
#if defined(CONFIG_STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE)
static JSON_H *_iot_make_wifi_evt_data(void)
{
    JSON_H *evt_item = JSON_CREATE_OBJECT();
    JSON_ADD_STRING_TO_OBJECT(evt_item, "component",  "main");
    JSON_ADD_STRING_TO_OBJECT(evt_item, "capability", "wifiInformation");
    return evt_item;
}

也就是说：只要不开 WiFi Update，这段代码压根不参与编译， 整个 STDK 里不会有人碰 wifiInformation 这个 capability。 官方文档 doc/WiFi_Update.md 第 11~13 行写得很直白： 

### Check List to implementing WiFi Update feature
1. CONFIG_STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE option enable in config file (sdkconfig).
2. Add wifiInformation capability in Device Profile.

注意这两条都是 WiFi Update 的前置条件，文档里一个字都没提离线诊断。

02依赖清单逐项判定

把「可能被怀疑」的每一项都拉出来，逐条给代码依据。

依赖项判定代码依据 / 说明
CONFIG_STDK_IOT_CORE_EASYSETUP_BLE=y 必需 Kconfig 里 OFFLINE_DIAGNOSTICS 明确 depends on STDK_IOT_CORE_EASYSETUP_BLE（src/Kconfig:47）。没有 BLE 就没有传输通道。
CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS=y 必需 默认值 n（src/Kconfig:46）。不开的话两个 handler 走 #else 分支，直接返回 IOT_ERROR_EASYSETUP_NOT_SUPPORTED（iot_easysetup_d2d_ble.c:2491-2505）。

一次完整 BLE OTM 握手 必需 Cmd 11/12 是加密的，密钥来自 Cmd 2 KeyInfo 的 ECDH 协商；且 _iot_easysetup_gen_payload 在 otm_confirmed == false 时直接拒绝 step ≥ 4 的请求（iot_easysetup_ble.c:231-236）。

任意其他 capability

WiFi 已连接 不需要 连不上时返回 "network_status": "disconnected"（iot_easysetup_d2d_ble.c:2272-2274），流程照常。

Device Profile 改动 不需要 不用重新在 Developer Workspace 提交 profile，不用重新发布。
容易踩的误区

「wifiInformation 里有 ssid，离线诊断也要报 ap_mac，所以肯定用了它」 —— 这是最常见的错误推理。 ap_mac 来自 iot_bsp_wifi_get_status(&wifi_info) 返回的 wifi_info.bssid（BSP 层直接问 WiFi 驱动要），跟 capability 的 ssid 属性没有半点关系。

03完整调用链（7 层）

下面这条链路是「App 写入 Cmd 11 → 设备回 connectionInfo」的完整路径。 每一层都标了文件与行号，可以对照源码逐层下钻。

BLE 协议栈收到 GATT 写入
src/port/bsp/esp32/iot_bsp_ble_esp32.c:284 ~ 360
ESP-IDF 的 ESP_GATTS_WRITE_EVT 回调里，把 param->write.value 原样交给上层注册的 write_cb。这一层只知道「某个特征值被写了多少字节」， 完全不懂业务。
分包重组：把 MTU 碎片拼回完整报文
src/easysetup/ble/iot_easysetup_ble_msg.c:107 es_msg_assemble()
报文头 9 字节（seqNumber / cmd / transactionId / totalSize|offset / continued / segLen）， 按 chunkDataContinued 判断还有没有后续包。拼完整后交给 iot_easysetup_ble_msg_handler()。 这是唯一处理「分包」的地方，上层看到的永远是完整 payload。
命令号合法性 + 解密
src/easysetup/ble/iot_easysetup_ble.c:482 iot_easysetup_ble_msg_handler()
先判 cmd < IOT_EASYSETUP_BLE_INVALID_STEP； 再调 _iot_easysetup_ble_msg_decrypt()（同文件 308 行）。 白名单 DEVICEINFO(0) / KEYINFO(1) / LOG_SYSTEMINFO(8) / LOG_GET_DUMP(9) 明文直通， 其余全部要 AES 解密 —— Cmd 11 就在「要解密」这一侧。
权限与序列校验（关键闸门）
src/easysetup/ble/iot_easysetup_ble.c:214 _iot_easysetup_gen_payload()
两道门：
① !otm_confirmed && cur_step >= WIFISCANINFO(4) → 只放行 LOG_SYSTEMINFO 和 LOG_GET_DUMP，其余返回 INVALID_CMD。
② 顺序校验 cur_step != ref_step（step < 8 时生效）。
通过后才 request.step = cur_step 往下传。
step 分派
src/easysetup/ble/iot_easysetup_d2d_ble.c:2523 iot_easysetup_get_response()
一个巨大的 switch ((enum iot_easysetup_ble_step)request.step)。 离线诊断占两个 case：
IOT_EASYSETUP_BLE_STEP_OFFLINE_DIAGNOSTICS_CONNECTION_INFO（值 10）
IOT_EASYSETUP_BLE_STEP_OFFLINE_DIAGNOSTICS_RECOVERY（值 11）
业务处理：拼 JSON
iot_easysetup_d2d_ble.c:2223 _es_offline_diagnostics_connection_info_handler()
整个函数 70 行，没有一行碰 capability。数据来源只有三处： iot_bsp_get_bsp_name()、iot_bsp_wifi_get_status() / iot_bsp_wifi_get_freq()、ctx->last_st_ecode。 产出 {"data":{...},"errorcode":0}。
加密 + Indication 回传
iot_easysetup_ble.c:443 iot_easysetup_ble_send_response()
先 iot_security_cipher_aes_encrypt()，再按 MTU 切成多个 Indication 包发出去。 大报文（比如 log dump 的 2KB）会自动切片。

3.1 第 6 层：业务函数逐行拆解

这是整个功能里唯一「有业务含义」的函数，值得逐行看。

/* iot_easysetup_d2d_ble.c:2223 */
#if defined(CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS)
STATIC_FUNCTION iot_error_t _es_offline_diagnostics_connection_info_handler(
        struct iot_context *ctx, char **out_payload)
{
    char *output_ptr = NULL;
    JSON_H *root = NULL, *data = NULL, *con_info = NULL;
    iot_error_t err = IOT_ERROR_NONE;
    iot_wifi_info wifi_info = {0};

    /* ---- 建三层 JSON 骨架：root -> data -> connectionInfo ---- */
    root  = JSON_CREATE_OBJECT();
    data  = JSON_CREATE_OBJECT();
    JSON_ADD_ITEM_TO_OBJECT(root, "data", data);
    con_info = JSON_CREATE_OBJECT();
    JSON_ADD_ITEM_TO_OBJECT(data, "connectionInfo", con_info);

    /* ---- ① 平台名：直接问 BSP，比如 "esp32s3" ---- */
    JSON_ADD_STRING_TO_OBJECT(con_info, "mnmo", iot_bsp_get_bsp_name());
    JSON_ADD_STRING_TO_OBJECT(con_info, "network_type", "wireless");

    /* ---- ② WiFi 状态：BSP 层查询，不走 capability ---- */
    iot_bsp_wifi_get_status(&wifi_info);
    if (wifi_info.wifi_status == IOT_WIFI_STATUS_CONNECTED) {
        char wifi_bssid[WIFIINFO_BUFFER_SIZE] = {0};
        struct iot_mac mac = wifi_info.bssid;

        JSON_ADD_STRING_TO_OBJECT(con_info, "network_status", "connected");
        snprintf(wifi_bssid, sizeof(wifi_bssid),
                 "%02X:%02X:%02X:%02X:%02X:%02X",
                 mac.addr[0], mac.addr[1], mac.addr[2],
                 mac.addr[3], mac.addr[4], mac.addr[5]);
        JSON_ADD_STRING_TO_OBJECT(con_info, "ap_mac", wifi_bssid);
        JSON_ADD_NUMBER_TO_OBJECT(con_info, "ap_freq", (double)iot_bsp_wifi_get_freq());
    } else {
        JSON_ADD_STRING_TO_OBJECT(con_info, "network_status", "disconnected");
    }

    /* ---- ③ 在线状态：只看内部错误码是否为 NONE ---- */
    if (ctx->last_st_ecode.ecode_type == IOT_ST_ECODE_NONE) {
        JSON_ADD_STRING_TO_OBJECT(con_info, "online_status", "online");
    } else {
        JSON_ADD_STRING_TO_OBJECT(con_info, "online_status", "offline");
    }
    JSON_ADD_STRING_TO_OBJECT(con_info, "last_error_code", ctx->last_st_ecode.ecode);

    JSON_ADD_STRING_TO_OBJECT(data, "version", "1.0");
    JSON_ADD_NUMBER_TO_OBJECT(root, "errorcode", 0);

    output_ptr = JSON_PRINT(root);
    IOT_INFO("connection_info result : %s", output_ptr);
    *out_payload = output_ptr;
out:
    if (root) JSON_DELETE(root);
    return err;
}

三个数据来源，没有一个来自 capability：

mnmo
iot_bsp_get_bsp_name() —— 芯片/平台名
network_status
ap_mac / ap_freq
iot_bsp_wifi_get_status() → wifi_info.wifi_status / .bssid；iot_bsp_wifi_get_freq()
online_status
last_error_code
ctx->last_st_ecode（iot_main.h:420 定义的结构体，STDK 内部状态，非 capability）
对照一下就能确认「不依赖 capability」

如果它真的调 capability，代码里必然出现 st_cap_send_attr()、caps_helper_xxx 或者 IOT_CAP_HANDLE。这段函数里一个都没有， 连 #include "st_dev.h" 都不需要。

5.1 Cmd 11 — connectionInfo

请求：无 payload，加密。

响应：data.version + data.connectionInfo，含 7 个字段：

字段类型取值 / 来源

network_typestring固定 "wireless"（以太网设备会是别的值）
network_statusstring"connected" / "disconnected"
ap_macstringMM:MM:MM:MM:MM:MM 大写十六进制，仅连接时出现

实际响应长这样：

{
  "data": {
    "connectionInfo": {
      "mnmo": "esp32s3",
      "network_type": "wireless",
      "network_status": "connected",
      "ap_mac": "A4:2B:B0:11:22:33",

文档与实现不一致（第 1 处）

5.2 Cmd 12 — recoveryCommand

两种命令，走同一个 handler。

restartThing — 重启设备

{ "data": { "command": "restartThing" } }

实现只有三行（iot_easysetup_d2d_ble.c:2413-2419）： 调 iot_command_send(ctx, IOT_COMMAND_SYSTEM_REBOOT, NULL, 0)， 走的是 STDK 的 main command 队列，最终由 BSP 的 iot_bsp_system_reboot() 执行。 先回响应再重启，否则 App 收不到确认。

updateWifi — 推送新 WiFi 凭据

{
  "data": {
    "command": "updateWifi",
    "wifiCredential": {
      "ssid": "MyAP",
      "password": "12345678",
      "macAddress": "...",
      "authType": 0,
      "hiddenSSID": 0,
      "hexSsid": "..."
    }
  }
}

hexSsid 是 base64url 编码的 SSID，用于含中文/特殊字符的 SSID； 如果扫描结果里带了 hexSsid，这个字段就是必填的。 解析逻辑在 _es_wifi_prov_parse()（iot_easysetup_d2d_ble.c:1728）， 用的是 BLE 自己那份，不是 HTTP 那份。

解析成功后依次做五件事：

1. 置标志
ctx->d2d_event_request = true、ctx->need_wifi_reset = true、connection_retry_count = 0
2. 触发重连
若有重试定时器则重建 2s 后触发，否则直接 iot_state_update(ctx, IOT_STATE_CLOUD_DISCONNECTED, 0)
3. 起 60s 兜底定时器
iot_os_timer_create(_offline_diagnostics_wifi_update_timeout, 60000, ctx)
4. 不立即回响应
返回 IOT_ERROR_EASYSETUP_REQUEST_PENDING，把连接挂住
5. 等重连结果
成功/失败都通过 offline_diagnostics_wifi_update_command_handler() 在同一 BLE 连接上回包
这是整条链路里最精妙的设计

updateWifi 不是「收下就回 OK」，而是真的等设备用新凭据连上云之后再告诉 App 结果。 BLE 连接全程保持，App 界面上那个转圈的「正在修复」就是在等这个包。 60 秒没结果才超时兜底。

06两套错误码体系

这里最容易看晕：设备侧有两套码，App 侧还有第三套。搞清对应关系，看日志才不迷路。

6.1 设备侧：STDK 内部 ecode（ctx->last_st_ecode）

07updateWifi 的状态闭环

把时序摊开看，这条路径比读代码直观得多。

关键代码在 iot_main.c:993-1004：

/* 重连成功分支 */
} else {
    ctx->connection_retry_count = 0;
    ctx->es_network_status = err;
    iot_set_st_ecode(ctx, IOT_ST_ECODE_NONE);      // 清错误码
#if defined(CONFIG_STDK_IOT_CORE_EASYSETUP_BLE)
    if (ctx->d2d_event_request) {
        if (ctx->offline_diagnostics_wifiupdate_timeout) {
            // 有诊断定时器 → 这是离线诊断发起的重连 → 回执
            offline_diagnostics_wifi_update_command_handler(ctx, NULL);
        } else {
            iot_easysetup_deinit(ctx);
        }
    }
#endif
}

d2d_event_request 这个标志就是「本次重连是离线诊断要求的」的标记。 没有它，重连成功后 BLE 会直接 deinit，App 那边永远等不到回执。

08六个实现细节与坑

这几条是读文档看不出来、只有对着代码才能发现的。

8.1 编译宏默认是关的

iot-core/src/Kconfig:44-49：

config STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS
    bool "Enable offline diagnostics functionality"
    default n                                    // ← 默认关闭
    depends on STDK_IOT_CORE_EASYSETUP_BLE       // ← 硬依赖 BLE
    help
       If this option is enabled, the device enable offline diagnostics functionality.

不开的话，iot_easysetup_d2d_ble.c:2490 的 #else 分支会把三个函数 全部替换成桩函数，直接返回 IOT_ERROR_EASYSETUP_NOT_SUPPORTED。 你的 sdkconfig.esp32s3 是 =y，所以是开着的。

8.2 otm_confirmed 是一道硬门槛

这条最容易被忽略。看 iot_easysetup_ble.c:231-236： 

if ((!context->otm_confirmed) && (cur_step >= IOT_EASYSETUP_BLE_STEP_WIFISCANINFO)) {
    if ((cur_step != IOT_EASYSETUP_BLE_STEP_LOG_SYSTEMINFO) &&
        (cur_step != IOT_EASYSETUP_BLE_STEP_LOG_GET_DUMP)) {
        err = IOT_ERROR_EASYSETUP_INVALID_CMD;   // ← 直接拒
        goto post_exit;
    }
}

WIFISCANINFO 的值是 4，而 CONNECTION_INFO 是 10， >= 4 成立，且不在两个白名单里 → 返回 INVALID_CMD。

也就是说：App 必须先走完 Cmd 1 → 2 → 3 → 4，把 otm_confirmed 置 true， 才能发 Cmd 11。

otm_confirmed 置 true 的位置场景
iot_easysetup_d2d_ble.c:1135 / 1185 / 1226 / 1257ConfirmInfo 里不同 OTM 方式校验通过（JustWorks / QR / SN / HashedSN）
iot_easysetup_d2d_ble.c:1348ConfirmInfo 处理结束
iot_easysetup_d2d_ble.c:1457Confirm（PIN 校验）通过
推论：全新未配网的设备用不了离线诊断

未配网时 App 走的是完整配网流程，otm_confirmed 会在流程中置 true， 但那时候设备还没 owned，广告包也不带 OWNED_STATE 位，App 根本不会把它列进「离线设备」。 离线诊断的适用对象只能是「已经配过网、但现在掉线」的设备。

8.3 BLE 生命周期被这个宏改写

这是开这个宏对系统唯一的副作用，在 iot_easysetup_ble.c:182-189： 

/* BLE 断开回调里 */
#if !(defined(CONFIG_STDK_IOT_CORE_EASYSETUP_WIFI_UPDATE) || \
      defined(CONFIG_STDK_IOT_CORE_EASYSETUP_OFFLINE_DIAGNOSTICS))
    // If there is no other ble service required except onboarding,
    // cleanup after onboarding complete.
    if (context->wifi_update_enabled) {
        _send_ble_deinit_request();      // 关掉 BLE
    }
#endif

逻辑是反的：只有当 WiFi Update 和离线诊断都没有开启时，配网完成后才会主动关 BLE。 开了任意一个，BLE 就一直保持着（广播 + 可连接），等着 App 随时回来连。

这也是为什么「配网完成后手机还能搜到设备」—— 不是 bug，是设计。 顺带解释了你之前测试时看到的现象：设备配完网 BLE 一直在广播。

8.4 last_st_ecode 掉电不恢复（BLE 路径的真实缺陷）

iot_set_st_ecode() 每次都会把错误码写进 NV（iot_api.c:1959）： 

err = iot_misc_info_store(IOT_MISC_PREV_ERR, (void *)ecode);

但读回来的地方只有两处，都在 HTTP 路径：

调用点路径
iot_easysetup_d2d_tcp.c:392HTTP over TCP 的 _es_deviceinfo_handler
iot_easysetup_d2d_tls.c:152HTTP over TLS 的 _es_deviceinfo_handler
缺失 BLE 路径_es_deviceinfo_handler（BLE 版）里没有 iot_misc_info_load(IOT_MISC_PREV_ERR, ...)

后果：设备冷启动后，如果本轮运行还没发生过网络错误， ctx->last_st_ecode 就是 NONE， Cmd 11 会报 "online_status": "online"、"last_error_code": ""， 哪怕上次掉电前确实存了一个 CE81。

同一个坑还影响 prevErrorCode（iot_easysetup_d2d_ble.c:569）， 它同样直接读 ctx->last_st_ecode.ecode。

实测时怎么绕

先让设备真的出一次错（比如关掉路由器等它重连失败），不要重启， 立刻用 App 触发离线诊断 —— 这时 last_st_ecode 还在内存里，能读到真实错误码。 重启后再测就只能拿到 UE01。

8.5 广告包里没有「支持离线诊断」这个独立位

文档说 OCF info 有四种组合，其中 0x03 表示 「Onboarded + WiFi update Support + Offline diagnostics Support」。 但代码里只判了一个条件（iot_easysetup_discovery_advertiser.c:136-141）：

if (ctx->wifi_update_enabled) {
    data[offset++] = OCF_INFO_ONBOARDING_SUPPORTED | OCF_INFO_OWNED_STATE;      // 0x03
} else {
    data[offset++] = OCF_INFO_ONBOARDING_SUPPORTED | OCF_INFO_ONBOARDING_READY; // 0x05
}

没有 offline_diagnostics_enabled 这样的运行时字段 （对比一下，wifi_update_enabled 是 iot_main.h:427 里真实存在的成员）。 也就是说 App 无法从广播包区分「这台设备支不支持离线诊断」， 只能靠 owned 状态 + 试探性发命令（收 NOT_SUPPORTED 就说明没开）。

8.6 文档与实现的其他出入

项文档写的代码实际
Cmd 11 响应字段 last_error_code / ap_mac / conn_rssi 无 conn_rssi；实际有 mnmo / network_type / network_status / ap_freq / online_status
Cmd 13 以太网事件 定义了完整请求/响应，含 timeout 字段和 544/401/501 错误码 enum iot_easysetup_ble_step 里没有对应 step，ESP32 侧完全未实现
Cmd 10 log/dump 标为「离线诊断」章节第一条（No Encryption） 实现是 _es_log_get_dump_handler，走的是 LOG_GET_DUMP(9)，与配网流程共用，不是诊断专属
错误码枚举数量 Offline_Diagnostics.md 里只提 OE10/OE20/OE21/OE30/OE31/OE33-x/OE34~37 iot_st_ecode_t 有 40 个枚举值，前缀是 UE/EE/NE/CE/DS，两套编号体系

Offline_Diagnostics.md 里的 OE10 / OE20 / OE21 / OE30 / OE31 / OE33-x / OE34-37 是 App 侧诊断引擎的分类编号（App check / Wi-Fi check / Cloud check）， 不是设备回的错误码。设备只回 last_error_code，两者在 App 内部做映射。

10.1 一句话记忆

给三周目 STDK 的一句话

Capability 是「设备对云端说的语言」，离线诊断是「设备对手机说的语言」。 前者走 MQTT、要在 Profile 里声明、受 rate limit 约束； 后者走 BLE、是编译期特性、完全绕过 capability 注册表。 wifiInformation 属于前者，服务于 WiFi Update；离线诊断属于后者，两者只是都跟 WiFi 有关而已。
